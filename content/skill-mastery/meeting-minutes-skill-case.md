# 会议纪要 Skill 实操案例

## 一句话解释

用一份 20 分钟模拟会议记录，对比"普通 Prompt"和"会议纪要 Skill Prompt"的输出差异，直观体验 Skill 如何让 AI 从"写出来"升级为"按标准稳定交付"。

## 适合谁

* 想亲眼看到 Skill 实际效果的人。
* 需要做会议纪要、客户会议记录或跨部门复盘的业务同事。
* 想理解 Skill 工作流如何落地到具体业务场景的人。

---

## Part 1：案例背景

### 会议场景

区域团队刚完成一场围绕"耐药菌感染管理与侵袭性真菌病诊疗路径优化"的城市级学术交流会。区域团队需要在会后快速复盘客户反馈、产品相关机会、医学支持需求、竞品动态、合规风险和后续行动计划。

### 参会角色

* 田悦（LMM，区域市场经理，会议主持）
* 刘明（DM，地区经理）
* 王佳（MICS，重点医院1负责人，覆盖ICU、感染科）
* 陈宇（MICS，重点医院2负责人，覆盖血液科、呼吸科）
* 周琳（MKT，中央市场同事）
* 陈博士（医学部 / MSL）

### 产品范围

耐药菌相关：思福诺、思福妥；真菌相关：康新博、威凡。

## Part 2：提示词对比

### 提示词 1：普通 Prompt

```text
请帮我整理一份会议纪要。
```

### 提示词 2：会议纪要 Skill Prompt

```text
请你作为"会议纪要 Skill"来处理我提供的会议记录。

你的任务不是简单总结会议内容，而是按照固定工作流，
把会议内容整理成一份可以推动后续行动的专业会议纪要。

请严格按照以下流程执行：

# Step 1：投入会议记录并识别输入信息
识别会议主题、背景、参会角色、讨论对象、关键产品/客户/部门。

# Step 2：判断会议类型
判断属于哪一种或多种类型（项目推进会/决策会/复盘会/客户会议/
周会/跨部门对齐会），说明判断理由和纪要重点。

# Step 3：选择纪要结构
必须包含：会议主题与背景、会议类型判断、核心结论、已确认事项、
待确认事项、风险与边界、后续行动项、给上级汇报的3条摘要。

# Step 4：提取关键信息
4.1 核心结论（只写已形成共识的内容）
4.2 已确认事项（已明确的事实、安排或决定）
4.3 待确认事项（尚未确认、需要后续核实的信息）
4.4 客户信号（客户反馈、资料需求、学术教育机会、竞品信号）
4.5 后续行动项（表格：行动项、责任人、截止时间、优先级、依赖条件）

# Step 5：质量检查
1.是否已判断会议类型
2.是否区分已确认和待确认事项
3.行动项是否都有责任人和截止时间
4.是否识别未审核材料、医学边界、竞品风险
5.是否避免把客户兴趣写成已确认合作
6.是否避免编造会议记录中没有的信息

# Step 6：交付结果
输出：完整会议纪要 + 后续行动项表 + 风险与边界清单 + 给上级汇报的3条摘要

注意：不要编造信息，不要把推测写成事实，不要输出具体医学治疗建议。
```

## Part 3：Skill 应识别出的关键信息

### 已确认事项

* 市一院 ICU 王主任明确提出耐药菌管理路径图 / 科室学习资料需求
* 市二院血液科李主任提出真菌风险分层、诊疗路径和病例复盘框架需求
* MKT 可在下周三前提供耐药菌路径图内部框架版，但不可对外使用
* 对外材料必须走审核流程
* 如果涉及真实病例，需要提前收集脱敏摘要，并由医学团队判断是否适合讨论

### 待确认事项

* 市一院 ICU 是否愿意开展院内耐药菌病例讨论或 MDT
* 市一院是否需要检验科、药学部共同参与
* 市二院血液科希望的会议形式、时间窗口、是否需要病例讨论
* 市三院呼吸科赵主任具体需要哪类威凡材料
* 竞品信息的具体公司、材料内容和影响程度均未确认

### 风险与边界

* 未审核材料不能对外使用
* 客户兴趣不能写成已确认合作
* 客户提到"病例效果不理想"不能写成产品负面反馈
* 竞品信息只能标注为客户口头提及，细节未确认
* 病例讨论不能替代临床决策，也不能形成具体处方建议

### 行动项（部分）

| 行动项 | 责任人 | 截止时间 |
|---|---|---|
| 确认市一院 ICU 耐药菌路径图/科室学习/MDT 的具体需求 | 王佳 | 本周三前 |
| 确认市二院血液科真菌科室会/病例复盘形式和时间窗口 | 陈宇 | 本周五前 |
| 输出耐药菌路径图内部框架版（标注仅内部讨论） | 周琳 | 下周三前 |
| 评估路径图和病例讨论框架的医学边界 | 陈博士 | 下周五前 |
| 输出 RM 汇报摘要 | 田悦 | 本周五前 |

## Part 4：对比要点

| 维度 | 普通 Prompt | Skill Prompt |
|---|---|---|
| 会议类型判断 | 不会判断，全部混在一起总结 | 先判断类型（复盘会 + 跨部门对齐会），再按类型决定重点 |
| 已确认 vs 待确认 | 不区分，全部写成"会议讨论了" | 明确区分已确认事实和待确认信息 |
| 行动闭环 | 可能遗漏责任人或截止时间 | 表格化，每项必有责任人和截止时间 |
| 风险边界 | 不识别合规、医学、竞品风险 | 主动识别未审核材料、医学边界、竞品口头信息 |
| 上级汇报 | 不输出 | 主动输出3条精炼摘要 |
| 编造风险 | 可能编造信息 | 明确要求"不要编造，不要把推测写成事实" |

## Part 5：有 Skill vs 无 Skill 对比实操（HTML 幻灯）

### 实操任务

用同一份"AI 基础理论课程 20 页幻灯大纲"，分别进行"无 Skill 生成"与"调用 frontend-slides Skill 生成"，直观体验两者在结构、视觉、风格统一性、交付质量上的差异。

### 对比提示词

**提示词 1：不调用任何 Skill**

```text
基于《AI基础理论_20页幻灯大纲》生成一套 20 页 16:9 HTML 幻灯片。
要求：不调用任何 Skill；输出单文件 HTML。
```

**提示词 2：安装并调用 frontend-slides Skill**

```text
请先安装并调用 frontend-slides Skill。
Skill GitHub：https://github.com/zarazhangrui/frontend-slides
我目前已有《AI基础理论_20页幻灯大纲》。
```

### 对比评分维度

* 风格统一性
* 页面结构多样性
* 信息层级清晰度
* 是否像正式培训课件
* 是否适合投影展示
* 是否减少二次返工
* 是否体现完整交付思维

### 核心收口

> 无 Skill：AI 在临场发挥。
> 有 Skill：AI 在按一套交付系统工作。
> Skill 的价值：不是让 AI 更会写，而是让 AI 更稳定地完成一类任务。
